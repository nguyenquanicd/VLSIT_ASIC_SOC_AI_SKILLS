# Measured closure contract, schema v2

<!-- VLSIT_TERMINOLOGY_START -->
Terminology: Register-Transfer Level (RTL); Design Under Test (DUT); Intellectual Property (hardware IP) (IP). See the [skill glossary](vlsit_glossary.md) for context and other abbreviations. Preserve identifiers and use the exact specification/tool revision.

Read for R-200, R-202, R-203 and R-260 to R-271. Plan validation, artifact
validation, measured closure and human sign-off are separate verdicts. Schema v1
observations are rejected for closure; they can remain historical evidence.

## 1. Commands and verdicts

```sh
python scripts/vlsit_verify_plan.py check vplan.csv --spec-index requirements.txt
python scripts/vlsit_verify_closure.py --vplan vplan.csv --spec-index requirements.txt --contract closure_contract.json --observations closure_observations.json --output closure_result.json
```

Exit 0 means MET without waivers by default; 1 means UNMET; 2 means invalid,
incomplete or untrusted input; 3 means MET_WITH_WAIVERS. `--require-no-waivers`
makes the default explicit. Only an explicit `--allow-waivers` permits exit 0 for
a conditional result; the JSON verdict and waived counts remain conditional.
No successful executed run means UNMET even when every obligation is waived.
Invalid input may return without a result file; CI must reject a missing result or nonzero exit, not reuse an older JSON file.
Use lowercase SHA-256 hex strings throughout and store each result under its immutable run/baseline directory.
An existing output requires `--force`; error/invalid input never grants closure.

The checker prints `CLOSURE_RESULT:` followed by JSON, including measured/waived
counts, per-metric recomputed coverage, N/A metric policies, contract/baseline
hashes and human_signoff=false. `--output` saves that report. CI must inspect the
verdict, not treat artifact-validation PASS as hardware verification success.

## 2. Frozen inventory, scenario scope and approval

Keep an approved requirement/protocol inventory: UTF-8, one ID per line, with
optional `#` comments. Plan checking reconciles it in both directions. Review
extraction against the specification; a list generated by AI is not automatically
complete. Keep out-of-scope requirements in a reviewed scope record.

Every vplan row needs unique obligation_id, configuration, dimension, checker/bin/
assertion IDs and test IDs. Stable IDs use semicolon separators. For measured
closure the row must be passing and its evidence field must name the accepted
run-receipt source ID. Failing, blocked or planned rows cannot silently become
closed. Update vplan and bug/fix history from new results before assessing closure;
retain superseded failed evidence in history. Waived rows require both the normal
plan waiver fields and a bound waiver approval record.

`scope_matrix` is a path/SHA-256 artifact. Its JSON has schema_version=2 and cells.
Each cell has req_id, configuration and dimensions. Every inventory/configuration
pair needs a cell, and every cell explicitly addresses normal, boundary, error,
recovery, reset, backpressure and concurrency. Extra project-specific dimensions
are allowed. A dimension contains dimension, applicability and obligations; required
needs non-empty obligation IDs, while not_applicable needs an empty list and a
technical reason. Each obligation belongs to exactly one matching cell/dimension.
One combined test can satisfy many obligations; obligation count is not testcase count.

The contract's `approval` references an approval JSON artifact. Its review contains
decision=approved, named approver and non-future ISO date. requirements_sha256 binds
the inventory bytes; contract_sha256 binds the canonical JSON of the contract
excluding only its approval field. Canonical JSON uses sorted keys, compact commas/
colons, UTF-8, ensure_ascii=False and no NaN. The scope matrix, metric policy,
qualification references and source baselines are therefore frozen by that digest.
Changes need a reviewed new contract, not silent lowering of targets after a run.

Approval files are auditable review records, not cryptographic identity proofs.
Trust and protect the review/CI repository; the checker cannot authenticate a person
whose name is typed into JSON or detect a deliberately fabricated entire evidence set.

## 3. Build baseline and actual compiled inputs

`baseline.specification` and `baseline.rtl_manifest` are path/SHA-256 artifacts
relative to the contract folder. Snapshot the specification under that folder.
The RTL/build manifest has schema_version=2, top, source_root, files and
configurations. source_root is portable and relative to the manifest folder; it
may explicitly refer to the real project source tree outside the evidence folder.
Each file path must stay inside that source_root and has sha256 plus role: rtl,
include, filelist, verification, model, build or configuration. List all resolved
compile inputs, including testbench and C/C++/Python model code, headers, generated
sources and dependency/configuration files. Duplicate resolved files are rejected.
The checker re-hashes every listed file; a changed or missing file blocks closure.

Configurations are unique objects with id, parameters, defines, options and tool
(including exact version). The contract configuration IDs must match them exactly.
Each run binds the specification/build hashes and configuration_sha256 (canonical
JSON of its full configuration object). Its build object records the actual top,
files, parameters, defines and options observed by the build producer; it must
match the approved manifest. Tool and command are recorded. Do not reconstruct
actual build inputs from expectations after the run: export them from the build.

The checker verifies listed inputs and receipt equality; finding an omitted dynamic
include or proving that an executable truly used a declared file still depends on
the qualified build producer/dependency export. Review that boundary explicitly.

## 4. Qualified producers, models and checkers

The contract lists producers, models and checkers. Artifact paths remain inside
the folder containing the referencing document, except the explicitly declared
build source_root. Unresolved template placeholders, missing hashes and duplicate
IDs fail validation.

A producer has id, implementation (path/hash of its actual adapter/reporter code)
and qualification (path/hash). Qualification names producer_id and the matching
implementation_sha256, plus review and tests. Required test kinds are raw_failure,
missing_bin, wrong_configuration, vacuity, invalid_counter and wrong_baseline.
Each qualification test needs kind, status=pass, actual command, integer exit_code=0,
expected and observed outcomes, and a hash-verified structured JSON evidence artifact.
That result artifact must exactly match those fields. Required expected outcomes are
match (known_answer/boundary/reset), handled (negative), detected (fault_detection)
and rejected (producer anti-false-PASS cases). A missing counter/result is unknown. Native reporters, vendor adapters and manual extraction tooling
need the same qualification/review record; a normalizer name alone is insufficient.

A model has id and contract artifact. Its model contract states provenance,
numeric_semantics, limitations, source_files (model-role paths in the build
manifest) and qualification. Model qualification binds model_id and
build_manifest_sha256, with known_answer, boundary, negative, reset and
fault_detection tests. Record language/tool version, numeric comparison and state/
reset behavior. Independent model correctness remains a reviewed technical judgment.

A checker has id, kind (protocol, scoreboard, model_compare or formal_adapter),
positive minimum_comparisons, model_id (or null for checks not using a model) and
qualification. Scoreboard/model_compare require a qualified model. Checker
qualification binds checker_id and build_manifest_sha256 and includes known_answer
and fault_detection evidence. Requalify after code/baseline changes. Normal runs
must show positive comparisons, zero mismatches/pending, expected=comparisons+
cancelled and observed=comparisons. Cancellation is allowed only when explicitly
permitted by the checker contract. No-op scoreboards cannot pass from a label alone.

## 5. Source receipts and raw result consistency

Observations have schema_version=2, baseline, sources, runs, metrics and waivers.
Sources have id, path, sha256 and role (run_receipt or waiver_record). Each run
references exactly one run_receipt source via source_ids. A receipt has schema
version 2, a qualified producer_id, run and raw_artifacts. Its run is exactly the
normalized run object with source_ids removed. Type-sensitive canonical JSON differences in test, seed, command, build/configuration,
baseline, counters or coverage reject the observation (false is not integer zero).

Raw artifacts have path, hash and role, relative to the receipt folder. They must
remain inside it. At least a distinct compile_log and simulation_log/formal_log
are required. Hash every log before extraction. The checker conservatively blocks
recognized anchored failure markers: SIMULATION FAILED, FATAL, %Error, UVM_ERROR
and UVM_FATAL; zero-count UVM summaries are allowed. This scanner is not a complete
vendor parser. Expected negative stimulus should be recorded by structured checker
results, not leave unclassified fatal/error markers in a passing log.

The producer must derive receipts from actual commands, tool exports and checker
results before normalization. Never synthesize a passing receipt to fit a desired
observation. Qualified adapters must interpret every tool-specific failure, timeout,
skipped test and merge result. Keep the raw reports plus reviewed extraction record.

A run contains id, test, configuration, seed, tool, command, baseline,
configuration_sha256, contract_sha256, build, compile, result, exit_code,
obligations, checks, bins, assertions, metric_hits and source_ids. All selected
runs must compile/execute successfully with integer exit code 0. Prior failed
baselines stay in history and are not relabelled passing.

## 6. Assertions and complete scenario checking

An obligation specifies id, req_id, configuration, dimension, checks, bins and
assertions (each with id and kind). Its IDs must match the vplan exactly. A single
accepted run must demonstrate the entire atomic obligation. Split multi-scenario
requirements into multiple obligations. Missing or unrelated property results fail.

Simulation results require status=pass and explicit failures, attempts, completed,
pending, disabled and cancelled counters. Failures and pending must be zero;
completed must be positive. Immediate properties require completed+disabled+
cancelled=attempts. Implications additionally require explicit antecedent_hits,
completed+cancelled=antecedent_hits and hits<=attempts-disabled. Cancellation needs
explicit property permission. Missing fields are unknown, never default-zero.

Formal properties require status=proved, proof_kind=unbounded, nonvacuity=pass,
failures=0, assumptions_id, assumptions_sha256 and hashed formal_assumptions/formal_report artifacts. The formal assertion definition references an approved assumptions artifact with id, configuration, specification_sha256, explicit constraints and review; its hash must match the proof and raw assumptions artifact.
Bounded/unknown/timeout results are not unbounded proof. Use separate bounded-check
obligations when that is the approved intent. Review assumption reachability,
clock/reset setup and proof scope; receipt metadata cannot establish theorem validity.

## 7. Coverage catalogs, metrics and merging

`metric_policy` explicitly addresses functional, code, assertion and mutation for
every configuration. applicable=false needs a reviewed technical reason and remains
visible in the result. Mandatory functional bins or assertion obligations cannot
have their corresponding coverage family marked N/A. Missing tool support must be
reported, not converted into a numeric coverage claim.

Metrics have id, configuration, family, scope, bin_ids, total and target_percent.
The universe is the unique bin_ids catalog, total must equal its cardinality, and
active targets must be finite and in (0,100]. Larger exported code catalogs can be
generated automatically; their source/tool mapping must be reviewed before approval.
Mandatory obligation bins must be present in the functional catalog. Freeze justified
exclusions in the approved universe; do not shrink it after measurements.

Each accepted run records actual functional bins and metric_hits (metric ID to
hit-bin IDs). Hits must belong to the matching configuration/catalog. Functional
hits must agree with bins; assertion hits must agree with checked property results.
Code/mutation hits come from the qualified producer's actual exports/campaign.
The checker computes a set union across successful bound runs, never sums duplicate
bins or averages percentages. Observations.metrics contains id, configuration,
run_ids, bin_ids, covered and total; these must exactly match recomputed data.
An aggregate 100000/100000 claim with only one measured bin is rejected.

## 8. Waivers and boundaries of the verdict

A waiver references source_id for a waiver_record artifact. Its payload exactly
matches the waiver with source_id removed: obligation_id, reason, owner, review,
expiry, contract_sha256 and baseline. Review must be approved and current; vplan
status must be waived with its normal waiver metadata. Waivers do not lower metric
targets or grant measured bins. Fully waived, unexecuted campaigns cannot claim closure.

MET means source-bound evidence meets this reviewed scope; MET_WITH_WAIVERS remains
conditional. Neither proves an unreviewed feature matrix complete, an oracle correct,
a tool honest or every possible hardware behavior covered. Qualified producers,
independent reviews and meaningful mutations remain part of the verification process.
No universal vendor parser, external IP model, simulator or formal solver is bundled.
